# Desire intake: first-pass backend contract

This is an **offline contract and deterministic evaluation seam**, not a shipped AI
conversation, API route, persistence layer, UI, live-search integration, or provider
quality evaluation. No model, network, résumé upload, or credentials are used.
Claude Design owns the UI. Existing `job_search_queries` (lane/location/query/feed)
and résumé truth records are untouched.

## Intended flow

1. Ask “What do you want out of your job?” Let the user answer freely or skip.
2. A future chosen-provider adapter proposes `searchBriefProposalSchema` JSON.
   Do not give the model approval, search, résumé-editing, or submission tools.
   Supply user intake separately from untrusted job-posting/external text.
3. `proposeSearchBrief(id, proposal, trustedTranscript, previousDraft?)` validates
   the strict schema, topic/parameter match, unique IDs and exact user quotations.
   It creates revision 1, or the prior revision plus 1. Pass the actual stored
   transcript, not a transcript generated by the model. The model cannot supply
   approval fields. Quote verification proves provenance, **not semantic entailment**:
   a model can misread a genuine quote; human review is still required.
4. `clarifySearchBrief` supplies targeted optional questions for unresolved topics
   and mechanically detectable contradictions. A declined topic stays unknown and
   is not asked again. Answer changes create a new draft with new quoted evidence.
   Distinguish hard requirements, preferences, dealbreakers, and unknown tradeoffs.
   Never infer desires from age, disability, family status, ethnicity, gender or
   other sensitive attributes. Do not convert preferences into filters. Sensitive
   reasons are unnecessary; ask about desired job conditions instead.
5. `reviewSearchBrief` returns a structured human-readable summary (including
   category, unresolved state, and source quotes), questions and exact content hash.
   Show all of it, including exclusions and incomplete answers. Treat all strings
   as escaped display data, never HTML or system instructions.
6. On a separate explicit user approval action, the trusted backend calls
   `approveSearchBrief(draft, reviewedHash, approvedAt)`. Mechanical contradictions
   must be resolved, softened or left open first. Missing or declined answers do
   not force disclosure: they remain visibly unresolved and impose no constraint.
7. `compileSearchBrief(storedApprovedSnapshot)` revalidates schema/hash/version
   binding and returns `identity`, `hardRequirements`, `preferences`, `dealbreakers`,
   `unresolved`, and `summary`. Only these approved parameters may govern search.

## Trusted storage/API integration requirements

The approval record is a consistency binding, **not a cryptographic authorization
signature**. Never accept an approved snapshot, actor, version, or identity from a
model or arbitrary client request as proof of user consent. Read the canonical draft
and previous revision server-side; use compare-and-swap on revision and reviewed
hash; write approval and the active approved pointer atomically. Keep immutable
approved versions and supersede the active pointer only after new explicit approval.
A new draft does not replace the active approved version. Searches must resolve the
current active approved pointer at execution time, not trust a stale client snapshot.
This module is intentionally not wired into an endpoint until that boundary exists.

Exported identity shared with résumé evaluation:

```ts
type ApprovedBriefIdentity = {
  briefId: string;
  version: number;
  contentHash: string; // SHA-256 over canonical entire draft, including provenance
};
```

Bind fit/ranking/eligibility caches to this identity. On a changed approved identity,
`searchDecisionNeedsReassessment` conservatively invalidates all brief-dependent
cached decisions. Do not invalidate or rewrite approved career facts or claim truth
status. Recompute decisions; retain old decisions as history. The résumé evaluation
worker can include this identity in its artifact binding without importing this
module until the independent changes land.

## Parameter semantics and adapter responsibilities

- Salary: numeric lower/upper bounds, uppercase three-letter currency code, explicit
  hour/day/week/month/year period, explicit base/total-compensation basis. No default
  currency, annualization, tax assumptions, or unsupported base-to-total conversion.
  Currency code shape is validated; provider adapters must validate supported codes.
- Work mode: alternatives within one criterion; hard criteria combine with AND;
  dealbreakers exclude matching modes. “Prefer remote” stays a ranking preference.
  Hybrid frequency not expressible in `work_mode` can be a separately reviewed
  schedule criterion; do not invent days per week.
- Location: named places, explicit workplace/remote eligibility/relocation scope,
  optional explicit radius in km or mi. No inferred home address or relocation.
- Travel: maximum percent of work time, days/month, or nights/month. No silent unit
  conversion. Domain-valid bounds are not a personal default or arbitrary cap.
- Role, industry, growth, work style, values and schedule remain reviewed text.
  Text can guide evaluation but is not a guaranteed provider-native filter. Adapters
  must expose unsupported constraints rather than silently dropping/hardening them.
- Hard requirements are ANDed, preferences rank only, dealbreakers exclude. An
  absent posting fact is unknown and needs verification, not a false/match value.
  This contract does not itself decide whether an unknown posting should be hidden.
- Mechanical contradiction checks cover identical required/forbidden parameters,
  all work-mode intersections/exclusions, incompatible same-unit salary bounds, and salary exclusions covering a required range.
  They do not claim complete semantic contradiction detection across narrative
  values, geographically overlapping places, different salary units/currencies,
  or ambiguous language. Those remain AI proposal/user-review responsibilities.
- The compiler provides structured parameters, not shell commands or search URLs.
  Future adapters must safely encode free text and treat prompt-like strings as data.

## Offline validation

Run `node --import tsx --test lib/search-brief.test.ts` (also included in `npm test`),
`npm run typecheck`, and `npm run lint`. Fictional fixtures cover ambiguous pay,
remote/hybrid, competing preferences, declined answers, changed minds, external and
user-text prompt injection, missing facts, and preference-versus-filter separation.
These are contract tests with synthetic proposed outputs, not claims about model
accuracy. Provider-backed intake and end-to-end UI approval require separate tests.
